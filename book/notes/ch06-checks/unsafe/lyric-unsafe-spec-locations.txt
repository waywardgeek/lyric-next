33:This is a design specification, not a description of a completed compiler or a proof of memory safety. Unless marked **Proposal**, **Open**, or **Deferred**, its rules describe the current intended language. Examples state contracts, not successful parser/compiler tests. Historical implementation behavior is evidence to examine, not permission to accept an unsafe construct.
344:Null is accepted only in nullable positions. Optional wrapping is implicit; unwrapping uses `!` or a checked conditional. No unsafe cast may manufacture an arbitrary live object reference.
769:An explicit unsafe benchmarking flag may disable bounds checks. Such builds are outside the safe-language guarantee and must be identified as unsafe in benchmark results.
895:The modifier means only that the consumer may destroy the current yielded object, subject to Section 12's current-only effect restrictions. It does not permit destruction of peer objects of the yielded class, arbitrary collection mutation, invalidating storage moves, or use of the current reference after destruction. For non-object yielded values it supplies no extra destruction operation; ordinary value/lifetime rules still apply. Both ordinary and safe generators must be memory-safe; the adjective describes the specific deletion permission, not an unsafe alternative execution mode.
930:Optional access is explicit. `x!` checks for null and unwraps; unsafe implicit nullable dereference is not a language feature.
1311:A deferred finalizer cannot run at an arbitrary point that bypasses static effects or class locking. Every point at which it may execute must account for its transitive destruction effects and hold all required locks. If the compiler/runtime cannot establish that, it must defer to a suitable boundary or reject the unsafe use. No concurrent background reclamation mechanism is implied by unspecified timing.
1715:Numeric covers i8/i16/i32/i64, u8/u16/u32/u64, f32/f64. Its factories return zero and one in T; add/mul have the same checked, wrapping-in-unsafe-mode, or IEEE behavior as the corresponding ordinary operators in Section 14. The capability does not silently widen T or promise algebraic identities that floating-point rounding or checked overflow would violate. User-defined conforming types may also supply the capability.
1725:Operands evaluate left to right. Numeric operations specify mathematical values or fixed-width bits explicitly; emitted C must preserve those semantics in safe and unsafe builds.
1760:Explicit unsafe mode disables automatic integer-overflow checks as well as the separately specified bounds-check opt-out. Ordinary integer addition, subtraction, multiplication, and negation then wrap modulo 2^N for an N-bit result type, with the resulting bits interpreted in that type. These operations have the same modular results as explicit wrapping arithmetic. Their result is defined even for signed overflow: the optimizer may not assume that overflow never occurs. The backend must implement these semantics deliberately rather than emit undefined signed C overflow and inherit its consequences.
1762:Unchecked bounds access remains outside the safe-language guarantee, and unsafe execution must be identified in benchmark results. Defined arithmetic wraparound does not restore memory safety to unchecked indexing. Shifts normalize counts in unsafe mode as specified below; division and remainder retain zero-divisor checks. Explicit wrapping operators retain their defined modular meaning in every mode.
1780:Integer `==`, `!=`, `<`, `<=`, `>`, and `>=` compare mathematical values across signedness and widths. The result is bool; no common numeric result type or explicit cast is required. This rule applies even when neither operand type contains the other's entire range, such as i64 versus u64. Safe and unsafe modes have identical comparison semantics.
1790:In safe mode, `as` preserves the mathematical value when it is representable in the destination type. A statically known out-of-range conversion is a compile-time error; a dynamic out-of-range conversion produces checked failure. In unsafe mode, integer `as` converts modulo 2^N for the N-bit destination and interprets the resulting bits in its signed or unsigned type.
1823:Integer division truncates toward zero. A nonzero remainder has the dividend's sign: `-7 / 3` is -2 and `-7 % 3` is -1. Division or remainder by zero produces a checked programming failure in both safe and unsafe modes; the absence of a meaningful modular result makes this an explicit retained check in unsafe mode.
1825:For signed minimum divided by -1, safe division produces checked overflow failure; unsafe division returns the signed minimum by modulo-width wraparound. The remainder for signed minimum and -1 is zero in either mode. These outcomes must be implemented before executing a backend instruction or C operation that has undefined behavior for the exceptional operands.
1831:Overflow checks have a real potential cost, especially for signed arithmetic; no zero-cost claim is made. Safe default behavior and explicit wrapping/unsafe choices make that tradeoff visible rather than dependent on optimization level.
1837:NaN compares unequal to every value, including itself. Equality with NaN is false, inequality is true, and ordered comparisons involving NaN are false. These rules apply in safe and unsafe modes; disabling integer/bounds checks does not authorize different floating-point values.
1861:These float-to-integer checks remain enabled in unsafe mode. They are an explicit exception to the integer-overflow/bounds opt-out, like zero-divisor checks. `!as` is restricted to integer-to-integer conversion; it does not define floating-point wrapping, saturation, or reinterpretation.
1912:Acquire at least shared class access **before** obtaining a borrowed reference to a shared object or object-owned storage. Reading a raw pointer first and locking afterward is unsafe: deletion and slot reuse could occur in between. Obtain references through a protected maintained relationship or another explicitly lifetime-safe source; root publication and acquisition contracts remain to be completed.
2195:`--soa` selects layout without changing language behavior. `--lir-dump` provides diagnostic output. A UAF-debug option is diagnostic support, not a substitute for static checking. Bounds-check disabling is an explicitly unsafe benchmark mode. Old RC-disable flags cannot silently change the accepted lifetime contract in an ordinary safe build.
